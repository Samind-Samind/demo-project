# ระบบเก็บ Audit Log และการปฏิบัติตาม PDPA

> สร้างเมื่อ 2026-08-02 จาก requirement ที่ผู้ใช้ระบุ

## ที่มา / บริบท

ผู้ใช้ต้องการเพิ่มระบบเก็บบันทึก (audit log) การเข้าถึง/แก้ไขข้อมูลของพนักงานและแอดมิน เพื่อให้สามารถตรวจสอบย้อนหลังได้ว่าใครทำอะไรกับข้อมูลของร้าน My Coffee Store เมื่อไหร่ พร้อมทั้งวางแนวทางการปฏิบัติตาม PDPA (พระราชบัญญัติคุ้มครองข้อมูลส่วนบุคคล) แบบเรียบง่ายเท่าที่จำเป็น

ระบบปัจจุบันของร้าน ([[20260802-001-table-self-order|Table Self-Order]] และ [[20260802-002-sales-dashboard|Sales Dashboard]]) ยังไม่มีระบบ login หรือเก็บข้อมูลลูกค้าเป็นรายบุคคล (ลูกค้าสั่งอาหารผ่าน QR code โดยไม่ต้อง login) ดังนั้น requirement นี้จึง**เน้น audit log ฝั่งพนักงาน/แอดมินเป็นหลัก** ส่วนประเด็น PDPA ให้ทำเท่าที่จำเป็นสำหรับสถานการณ์ปัจจุบัน และเตรียมแนวทางแบบง่ายไว้รองรับกรณีที่ระบบจะเก็บข้อมูลส่วนบุคคลของลูกค้าในอนาคต (เช่น เบอร์โทรสำหรับสมัครสมาชิก) โดยไม่ต้องสร้างระบบ consent management เต็มรูปแบบ

## Feature Requirements

- **Access log**: เก็บบันทึกทุกครั้งที่พนักงาน/แอดมินเข้าถึง (เปิดดู) ข้อมูลที่สำคัญ เช่น เปิดหน้า Sales Dashboard, เปิดดูรายละเอียดออเดอร์/บิลของโต๊ะ, เปิดดู audit log เอง
- **Event log**: เก็บบันทึกทุกครั้งที่พนักงาน/แอดมินมีการแก้ไข/เปลี่ยนแปลงข้อมูล เช่น เข้า/ออกระบบ (login/logout), เปลี่ยนสถานะออเดอร์ (รอทำ/กำลังทำ/เสร็จแล้ว), แก้ไขเมนู/ราคา, export รายงานยอดขายเป็น PDF, แก้ไขสิทธิ์ผู้ใช้งาน
- แต่ละรายการ log ต้องเก็บอย่างน้อย: รหัสพนักงาน/แอดมิน (staff/user ID), วันเวลาที่เกิดเหตุการณ์ (timestamp), ประเภท action, ข้อมูล/ทรัพยากรที่ถูกเข้าถึงหรือแก้ไข (เช่น หมายเลขโต๊ะ, รหัสออเดอร์, ชื่อเมนู) โดย**ห้ามเก็บข้อมูลส่วนบุคคล (PII) เกินความจำเป็น** — เก็บเฉพาะข้อมูลอ้างอิง (ID) ไม่เก็บเนื้อหาข้อมูลแบบเต็ม (เช่น ไม่เก็บสำเนาข้อมูลลูกค้าทั้งชุดไว้ใน log)
- กำหนดระยะเวลาการเก็บ log (retention) และมีกระบวนการลบ log อัตโนมัติเมื่อครบกำหนด
- ควบคุมสิทธิ์การเข้าถึง log ให้สอดคล้องกับสิทธิ์แบบ role-based ที่ใช้ใน [[20260802-002-sales-dashboard|Sales Dashboard]] คือ เจ้าของร้าน/ผู้จัดการเท่านั้นที่ดู log ได้ พนักงานทั่วไปไม่มีสิทธิ์เข้าถึง log
- เตรียมกลไก **consent แบบง่าย** สำหรับอนาคต: หากระบบมีการเก็บข้อมูลส่วนบุคคลของลูกค้า (เช่น เบอร์โทรสำหรับสมัครสมาชิก) ต้องมีการแสดงข้อความขอความยินยอมและบันทึกสถานะ (ยินยอม/ไม่ยินยอม) พร้อมวันเวลาที่ให้ความยินยอมไว้แบบง่าย ไม่ต้องมีระบบจัดการ consent ที่ซับซ้อน (เช่น ไม่ต้องมีการแบ่งประเภทความยินยอมหลายระดับ หรือระบบถอนความยินยอมแบบเต็มรูปแบบ)

## User Stories / Use Cases

- ในฐานะเจ้าของร้าน ฉันต้องการดูประวัติการเข้าถึง/แก้ไขข้อมูลของพนักงานแต่ละคน เพื่อตรวจสอบเมื่อเกิดข้อผิดพลาดหรือข้อสงสัย (เช่น ยอดขายไม่ตรง, สถานะออเดอร์ถูกแก้ผิดปกติ)
- ในฐานะผู้จัดการ ฉันต้องการรู้ว่าใครเข้าถึง Sales Dashboard และ export รายงานเมื่อไหร่ เพื่อควบคุมการเข้าถึงข้อมูลที่ละเอียดอ่อนของร้าน
- ในฐานะระบบ เมื่อพนักงานเปลี่ยนสถานะออเดอร์ แก้ไขเมนู หรือเข้าถึงข้อมูลสำคัญ ระบบต้องบันทึก log โดยอัตโนมัติโดยพนักงานไม่ต้องทำอะไรเพิ่ม
- ในฐานะเจ้าของร้าน ฉันต้องการให้ log เก่าที่เกินระยะเวลาที่กำหนดถูกลบออกโดยอัตโนมัติ เพื่อไม่ให้เก็บข้อมูลไว้นานเกินความจำเป็น
- ในฐานะเจ้าของร้าน หากในอนาคตต้องเก็บเบอร์โทรลูกค้าสำหรับระบบสมาชิก ฉันต้องการให้ระบบขอความยินยอมจากลูกค้าก่อนแบบง่ายๆ และมีหลักฐานว่าลูกค้ายินยอมแล้ว

## Business Rules

- ต้องเก็บ log อย่างน้อย 2 ประเภท: access log (การเข้าถึง/เปิดดูข้อมูล) และ event log (การแก้ไข/เปลี่ยนแปลงข้อมูล) ของพนักงานและแอดมินเท่านั้น (ไม่รวมลูกค้า เนื่องจากลูกค้าไม่มี login ในระบบปัจจุบัน)
- ข้อมูลใน log แต่ละรายการต้องมีอย่างน้อย: staff/user ID, timestamp, ประเภท action, ทรัพยากร/ข้อมูลที่ถูกเข้าถึง (อ้างอิงด้วย ID เท่านั้น) — ห้ามเก็บข้อมูลส่วนบุคคลแบบเต็ม (data minimization)
- ระยะเวลาเก็บ log (retention) กำหนดไว้ที่ **12 เดือน** นับจากวันที่บันทึก log นั้นเกิดขึ้น เมื่อครบกำหนดให้ระบบลบ log รายการนั้นออกโดยอัตโนมัติ (เลือกระยะเวลานี้เพื่อให้ตรวจสอบย้อนหลังได้ครบรอบปีบัญชี โดยไม่เก็บข้อมูลไว้นานเกินจำเป็นตามหลัก data minimization ของ PDPA — หากผู้ใช้ต้องการระยะเวลาอื่น สามารถปรับได้ในเอกสารออกแบบเชิงเทคนิคต่อไป)
- สิทธิ์การเข้าถึง (ดู) audit log จำกัดเฉพาะ role เจ้าของร้าน/ผู้จัดการ ตามแนวทางเดียวกับสิทธิ์ใน [[20260802-002-sales-dashboard|Sales Dashboard]] พนักงานทั่วไปไม่สามารถดู log ได้ แม้แต่ log ของตัวเอง
- ห้ามแก้ไขหรือลบ log ก่อนถึงกำหนด retention ด้วยมือ (log ต้องเป็น append-only เพื่อรักษาความน่าเชื่อถือของหลักฐาน) ยกเว้นกระบวนการลบอัตโนมัติเมื่อครบกำหนดเท่านั้น
- หากในอนาคตมีการเก็บข้อมูลส่วนบุคคลของลูกค้า ต้องมีการแสดงข้อความขอความยินยอมก่อนเก็บข้อมูลทุกครั้ง และบันทึกสถานะความยินยอม (ยินยอม/ไม่ยินยอม) พร้อมวันเวลาไว้อย่างง่าย โดยไม่ต้องมีระบบจัดการความยินยอมที่ซับซ้อน (ไม่ต้องมี consent versioning, ไม่ต้องมีระบบถอนความยินยอมแบบเต็มรูปแบบ, ไม่ต้องมี consent ต่อวัตถุประสงค์ย่อยหลายแบบ)

## ขอบเขต (Scope)

### สิ่งที่ทำ (In Scope)
- Audit log (access log + event log) สำหรับการกระทำของพนักงาน/แอดมินในระบบ [[20260802-001-table-self-order|Table Self-Order]] และ [[20260802-002-sales-dashboard|Sales Dashboard]]
- การกำหนดข้อมูลที่เก็บใน log แต่ละรายการ โดยคำนึงถึงหลัก data minimization
- นโยบายระยะเวลาเก็บ log (retention) และการลบ log อัตโนมัติเมื่อครบกำหนด
- การควบคุมสิทธิ์เข้าถึง log แบบ role-based (เจ้าของร้าน/ผู้จัดการเท่านั้น)
- แนวทาง consent แบบง่าย สำหรับเตรียมรองรับการเก็บข้อมูลส่วนบุคคลของลูกค้าในอนาคต

### สิ่งที่ไม่ทำ (Out of Scope)
- ระบบ consent management เต็มรูปแบบ (เช่น consent versioning, การถอนความยินยอมแบบละเอียด, consent ต่อวัตถุประสงค์ย่อยหลายแบบ)
- ระบบจัดการคำร้องขอของเจ้าของข้อมูล (Data Subject Access Request / DSAR) แบบอัตโนมัติ
- ระบบ log สำหรับพฤติกรรมลูกค้า (เนื่องจากลูกค้าไม่มี login/บัญชีผู้ใช้ในระบบปัจจุบัน)
- การเข้ารหัสข้อมูล (encryption) หรือสถาปัตยกรรมความปลอดภัยเชิงลึกอื่นๆ ซึ่งจะกำหนดรายละเอียดในเอกสารออกแบบเชิงเทคนิคต่อไป
- การเก็บข้อมูลส่วนบุคคลของลูกค้าจริง (เช่น ระบบสมาชิก/เบอร์โทร) — requirement นี้เตรียมแนวทาง consent ไว้ล่วงหน้าเท่านั้น ส่วนตัวระบบสมาชิกเองถือเป็น requirement แยกต่างหากในอนาคต

## เอกสารอ้างอิง

- [[index|01-spec]]
- [[20260802-001-table-self-order|ระบบสั่งกาแฟด้วยตนเองจากโต๊ะ (Table Self-Order)]] — แหล่งเหตุการณ์ที่พนักงาน/บาริสต้าทำ ซึ่งต้องถูกบันทึกใน event log
- [[20260802-002-sales-dashboard|หน้า Dashboard สรุปยอดขาย (Sales Dashboard)]] — ใช้แนวทาง role-based access เดียวกันในการกำหนดสิทธิ์ดู audit log

---

**หมายเหตุการตัดสินใจระหว่างจัดทำเอกสารนี้:**

Requirement ดิบที่ได้รับมาระบุแนวทางหลักไว้ค่อนข้างชัดเจนแล้ว (เน้น audit log ฝั่งพนักงาน/แอดมิน, consent แบบง่ายเท่าที่จำเป็น, ไม่ต้องมี consent management ซับซ้อน) จึงไม่ได้ถามคำถามเพิ่มเติมกับผู้ใช้ แต่มีการตัดสินใจเองในประเด็นที่ requirement ดิบไม่ได้ระบุตัวเลขชัดเจน โดยอิงหลัก data minimization ของ PDPA และความสอดคล้องกับเอกสารเดิมในโปรเจกต์:

| ประเด็น | การตัดสินใจ | เหตุผล |
|---|---|---|
| ระยะเวลาเก็บ log (retention) | 12 เดือน แล้วลบอัตโนมัติ | สมดุลระหว่างตรวจสอบย้อนหลังได้ครบรอบปีบัญชี กับหลัก data minimization ของ PDPA ที่ไม่ควรเก็บข้อมูลนานเกินจำเป็น (ปรับได้ในขั้นออกแบบเชิงเทคนิค) |
| สิทธิ์เข้าถึง log | เจ้าของร้าน/ผู้จัดการเท่านั้น | สอดคล้องกับ role-based access ที่กำหนดไว้แล้วใน [[20260802-002-sales-dashboard|Sales Dashboard]] |
| สร้างเอกสารใหม่ vs แก้เอกสารเดิม | สร้างเอกสารใหม่แยกต่างหาก พร้อมลิงก์อ้างอิงถึง Table Self-Order และ Sales Dashboard | เป็นหัวข้อ cross-cutting concern (audit/security/compliance) คนละเรื่องกับ feature เดิม แม้จะอ้างอิงถึงเหตุการณ์ในระบบเดิมก็ตาม จึงไม่ควรผสมเข้าไปในเอกสาร feature ที่มีอยู่ |
